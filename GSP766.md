# GSP766 – Managing a GKE Multi-tenant Cluster with Namespaces

## Known lab traps (read first)

1. Wait for the blue "Provisioning Lab Resources" message to disappear before starting. The cluster and datasets take about 5 minutes.
2. The lab says to test the service account "in a new tab". Cloud Shell tabs share the same gcloud login, so activating the service account switches every tab to it, and the later quota steps then fail as team-a-dev. Here the test runs in one tab and switches straight back to your student account.
3. The lab's `export ZONE=placeholder` lines don't work as written. The Setup block reads the real zone from the cluster.
4. `kubectl edit` opens nano, which is hard to follow on video. The quota change to 6 pods uses one `kubectl patch` command instead, with the same result.
5. The lab's commands use dollar-sign variables, which get mangled when copied. Everything below uses saved values.
6. The lab's scheduled query (`bq query --schedule`) is broken: its authorization link uses Google's retired copy-paste sign-in, so you can never get a version_info code. Task 5 creates the table with a normal query, then creates the scheduled query in the BigQuery Console, which is what the checker looks for.

## Task 3 – Access control in namespaces

Block 1 – IAM role, Kubernetes role and role binding, key:

```bash
cd ~/gke-qwiklab
kubectl config set-context --current --namespace=team-a
gcloud projects add-iam-policy-binding `cat ~/project` \
  --member=serviceAccount:team-a-dev@`cat ~/project`.iam.gserviceaccount.com \
  --role=roles/container.clusterViewer --condition=None > /dev/null
kubectl create role pod-reader --resource=pods --verb=watch --verb=get --verb=list -n team-a
kubectl create -f developer-role.yaml
kubectl create rolebinding team-a-developers --role=developer \
  --user=team-a-dev@`cat ~/project`.iam.gserviceaccount.com -n team-a
gcloud iam service-accounts keys create /tmp/key.json --iam-account team-a-dev@`cat ~/project`.iam.gserviceaccount.com
```

## Task 4 – Resource quotas

Block 1 – pod-count quota (the third pod is supposed to fail):

```bash
cd ~/gke-qwiklab
kubectl create quota test-quota --hard=count/pods=2,count/services.loadbalancers=1 --namespace=team-a
kubectl run app-server-2 --image=quay.io/centos/centos:9 --namespace=team-a -- sleep infinity
kubectl run app-server-3 --image=quay.io/centos/centos:9 --namespace=team-a -- sleep infinity
kubectl describe quota test-quota --namespace=team-a
```

You should see "exceeded quota: test-quota" for app-server-3, and the quota showing 2 of 2 pods used.

Block 2 – raise the limit to 6 pods (same as the lab's nano edit):

```bash
kubectl patch resourcequota test-quota -n team-a --type=merge -p '{"spec":{"hard":{"count/pods":"6"}}}'
kubectl describe quota test-quota --namespace=team-a
```

The Hard column for count/pods should now say 6.

Block 3 – CPU and memory quota, plus the demo pod:

```bash
cd ~/gke-qwiklab
kubectl create -f cpu-mem-quota.yaml
kubectl create -f cpu-mem-demo-pod.yaml --namespace=team-a
sleep 5
kubectl describe quota cpu-mem-quota --namespace=team-a
```

You should see limits.cpu 400m and requests.cpu 100m used.

## Task 5 – Monitoring and GKE usage metering

The Monitoring dashboard and Metrics Explorer steps aren't scored. Follow the lab in the Console if you want to show them.

Block 1 – turn on usage metering:

```bash
gcloud container clusters update multi-tenant-cluster --zone `cat ~/zone` --resource-usage-bigquery-dataset cluster_dataset
```

Block 2 – build the cost breakdown query from the template:

```bash
cd ~
sed \
  -e "s/.{fullGCPBillingExportTableID}/`cat ~/project`.billing_dataset.gcp_billing_export_v1_xxxx/g" \
  -e "s/.{projectID}/`cat ~/project`/g" \
  -e "s/.{datasetID}/cluster_dataset/g" \
  -e "s/.{startDate}/2020-10-26/g" \
  ~/gke-qwiklab/usage_metering_query_template.sql > cost_breakdown_query.sql
grep -c "fullGCPBillingExportTableID\|{projectID}\|{datasetID}\|{startDate}" cost_breakdown_query.sql
```

The count should be 0, which means every placeholder was filled in.

Block 3 – create the cost breakdown table:

```bash
cd ~
bq query --project_id=`cat ~/project` --use_legacy_sql=false \
  --destination_table=cluster_dataset.usage_metering_cost_breakdown --replace=true \
  "`cat cost_breakdown_query.sql`" > /dev/null && echo table-created
bq ls cluster_dataset
```

You should see table-created, and usage_metering_cost_breakdown in the list.

Block 4 – the scheduled query, in the Console. The checker needs a scheduled query, not just the table. The lab's `bq query --schedule` command can't create it, because its sign-in link (version_info) uses Google's retired copy-paste flow. Press Ctrl+C if you're stuck at that prompt. Creating it from the service account doesn't work either, because the lab doesn't let you give that account BigQuery access. The Console route works:

1. Print the query and copy all of it. If the terminal copy is messy, open the file in the Editor instead.

```bash
cat ~/cost_breakdown_query.sql
```

2. Console > BigQuery > open a new query tab (+) and paste the query. Don't click Run.
3. Click Schedule, then Create new scheduled query.
4. Name: GKE Usage Metering Cost Breakdown Scheduled Query
5. Repeat frequency: Days. At: any valid UTC time in HH:MM form, for example 23:30. Keep Start now and End never.
6. Tick "Set a destination table for query results". Dataset: cluster_dataset. Table Id: usage_metering_cost_breakdown. Write preference: Overwrite table.
7. Click Save and approve the sign-in popup with your student account.

Wait about a minute.

Click Check my progress: Monitoring GKE and GKE usage metering (40 points). Turning on usage metering earns the first 20; the scheduled query earns the second 20.
